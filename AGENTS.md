# AGENTS.md — правила работы в этом репозитории

Этот файл читают все агенты (Claude Code через CLAUDE.md, Codex — напрямую, и другие).
Он короткий намеренно. Подробности — в `agents/skills/*` и `docs/playbooks/*`, читай их, когда нужно.

## Кто мы
Команда людей и ИИ-агентов делает MVP на хакатоне. Задачи — в GitHub Issues.
Работа координируется только через `hk` (CLI или MCP-инструменты `hk_*`). Не договаривайся «в чате».

**Порядок:** ТЗ (`docs/tz.md`) → разбор ТЗ со сценарием демо (навык `hk-tz-analysis`) → план (`hk-kickoff`) → утверждение → задачи → код.
До утверждения плана продуктовый код не пишется. Приоритет всегда у того, что видно в сценарии демо.

## Цикл работы (обязателен)
1. `hk task next [--area <зона>] [--tier <low|mid|high>]` — получить задачу.
2. `hk task claim <id>` — взять её. Работай **только** в созданном worktree/ветке.
3. Прочитай задачу (`gh issue view <id>`), особенно **критерии приёмки**.
4. Сначала тесты по критериям приёмки, потом реализация.
5. `hk check` — пока не станет зелёным. Засчитывается только полный прогон: `hk check --only <шаг>` — для отладки.
6. `hk commit -m "feat: ..."` — коммит с trailers (не используй голый `git commit`). Работает только в ветке задачи.
7. `hk pr open` — сдать работу. После правок по ревью — снова `hk commit` и `hk pr open` (второй PR не создастся). Затем `hk task next`.

**Аренда.** Задача твоя, пока ты активен: `hk check` и `hk commit` продлевают аренду сами. Думаешь или ждёшь дольше 30 минут без них — `hk task heartbeat <id>`. Если команда вернула `lease_lost`, задачу отдали другому: не пушь свою ветку, оставь в issue заметку, что успел, и возьми новую.

Каждая команда `hk` возвращает JSON: `status`, `summary`, `next_actions`, `artifacts`, `error`.
**Делай то, что написано в `next_actions`.** При ошибке смотри `error.retry` и `error.stop_when`.

## Исполнитель и его субагенты
Задачу берёт **исполнитель** — агент, который сделал `hk task claim`. Он как подрядчик: может по надобности звать своих субагентов, но **сдаёт работу и отвечает за неё он сам**.
- Субагентам можно: искать по коду и документации, писать тесты и код по заданию исполнителя, проверять его код перед сдачей (code-reviewer, security-reviewer), запускать `hk check`.
- Только исполнитель: `hk task next` / `claim` / `release` / `status`, `hk commit`, `hk pr open`. Субагент новую задачу не берёт и PR не сдаёт.
- Субагенты работают в worktree задачи и в её зоне. Параллельно — только чтение и поиск; правки в одни и те же файлы — по очереди, иначе перезапишут друг друга.
- Ревью субагента перед сдачей полезно, но это **не** ревью для `hk-guard`: засчитывается только ревью другого агента (`hk pr review` не от исполнителя и не от его субагентов).
- Каждый субагент тратит лимиты подписки того, чей это ноутбук. Зови их, когда это реально ускоряет задачу.

**Кому что поручать (экономия лимитов).** Исполнитель на старшей модели думает и проверяет, работу делают помощники подешевле:

| Помощник | Модель (`hk.config.json → tiers`) | Поручай |
|---|---|---|
| `scout` | low — Claude: haiku | поиск по коду, чтение документации, прогон `hk check` с кратким пересказом ошибок. Ничего не меняет |
| `implementer` | mid — Claude: sonnet | код или тесты по чёткому поручению: что, в каких файлах, по каким критериям |
| исполнитель сам | high — Claude: opus | разбор задачи, решения, контракты, проверка работы помощников, `hk commit`, `hk pr open` |

- Не зови старшую модель субагентом для того, что делает `scout` или `implementer`.
- Субагент начинает с нуля: ему каждый раз пересказывают задачу. Мелочь на пару минут дешевле сделать самому.
- Работу помощника проверяй перед `hk commit` — отвечаешь за неё ты.
- В Codex роли — это навыки `role-scout`, `role-implementer`; модели по уровням — `hk.config.json → tiers.<уровень>.codex`.

**Отдельная задача или субагент?** Кусок, который можно отдельно смержить и показать (своя зона, свои критерии приёмки), — отдельная задача в очереди (`hk task status <id> blocked --note "нужна задача: …"` или фидбек planner'у). Кусок, нужный только внутри твоей задачи (поиск, тесты, черновая проверка, рутинная правка в твоей зоне), — субагент.

**Задачи `risk:high`: тесты пишет другой агент.** У каждой такой задачи (кроме каркаса) есть парная задача на тесты (`tests_for`).
- Задача на тесты: пишешь приёмочные тесты по критериям основной задачи **только** в `tests/pending/<T>/`. Продуктовый код не пишешь. CI эти тесты пока не запускает.
- Основная задача ждёт задачу на тесты. Её исполнитель — **другой агент** (`hk task claim` откажет тому, кто писал тесты). Первым коммитом он переносит тесты без изменений: `git mv tests/pending/<T>/* tests/acceptance/`, затем пишет код, пока они не позеленеют.
- `hk-guard` проверяет: задача на тесты не трогает ничего, кроме своей папки; тесты из `tests/pending/` не правятся и не удаляются; основная задача перенесла их все без единой изменённой строки.
- Тест неверный? Не правь — `hk task status <id> blocked --note "тест X: …"`. Его исправит новая задача с `changes_acceptance`.

**Имя агента.** `hk` сам добавляет к `HK_AGENT` имя машины (`claude@petya-laptop`) — так агенты разных людей различаются. Несколько сессий на одной машине — задай каждой свой `HK_AGENT_ID` (`claude@petya-2`).

## Когда остановиться
- Одна и та же ошибка 3 раза → `hk task status <id> blocked --note "что пробовал, что мешает"`.
- Задача неясна или критерии приёмки не проверяемы → `hk task status <id> needs-spec --note "вопрос"`. Не угадывай.
- Нужно изменить чужую зону или `contracts/` → не меняй, `blocked` с описанием.
- Задача не по силам → `hk task release <id> --note "что успел"`.
- Есть открытый issue с меткой `hk:pause` → закончи текущий шаг и остановись. Это проверяет код: `hk task next` и `hk task claim` вернут ошибку `paused`, пока человек не закроет issue.

## Границы
- Трогай только файлы своей зоны (`area:*` в задаче → пути в `hk.config.json` → `areas`).
- `contracts/` — источник правды для API между зонами. Код подгоняется под контракт, не наоборот.
- Приёмочные тесты своей задачи пишешь **первым коммитом**, новыми файлами в `tests/acceptance/` (каждый Given/When/Then проверяется тестом). **Существующие** приёмочные тесты не меняешь и не удаляешь — PR не пройдёт `hk-guard`, если задача не перечисляет их в разделе «Меняет приёмку».
- `hk.config.json`, `.github/`, `AGENTS.md`, `CLAUDE.md`, `agents/`, `events/` не меняешь никогда — это правила, их меняет только разработчик harness. Нужна правка → `blocked` с описанием.
- Один PR = одна задача. Маленькие PR лучше больших.

## Запрещено
- Секреты, ключи, токены в коде и коммитах. Только `.env` (в .gitignore) и `.env.example` с пустыми значениями.
- `git push --force`, переписывание истории, коммиты напрямую в `main`.
- Создавать аккаунты, вводить пароли и платёжные данные — это делают люди.
- Публиковать что-либо наружу (посты, сообщения, деплой в прод) без явного решения человека.
- Отключать или обходить проверки (`--no-verify`, пропуск тестов, `skip`), чтобы позеленеть.
- `gh pr merge --admin`, ручная постановка статусов, ревью собственного PR, правка чужих маркеров `hk:review`.

## Definition of Done
- [ ] Все критерии приёмки покрыты тестами, тесты зелёные (`hk check`).
- [ ] Контракт соблюдён, демо-путь (`tests/e2e/`) не сломан.
- [ ] PR открыт через `hk pr open`, в описании — что сделано.
- [ ] Ревью сделал **другой агент** (по возможности другого вендора: код Claude ревьюит Codex, и наоборот) по навыку `hk-review` и записал вердикт `hk pr review <n> --verdict approve`. Статус `hk-guard` зелёный — дальше PR сливается сам (`risk:high` мержит integrator).

## Уровни тестов
| Что | Требование |
|---|---|
| Демо-путь | E2E «счастливого пути», на каждый мерж в main. `main` всегда демо-готов |
| Границы зон | контрактные тесты с обеих сторон |
| Затронутая зона | регрессионный тест на каждый фикс бага; явные краевые случаи из критериев |
| LLM-вызовы в тестах | только через записанные фикстуры, без сети |

## Стиль
- Conventional Commits: `feat:`, `fix:`, `test:`, `refactor:`, `docs:`, `chore:`.
- Форматирование и линт — забота автоматики (`hk check`), не трать на это ревью.
- Нет скрытых договорённостей: правило, которого нет здесь или в линтере, не существует.

## Где что лежит
- `hk.config.json` — зоны, проверки, уровни моделей, MCP.
- `agents/roles/` — роли (planner, builder, reviewer, integrator). `agents/skills/` — навыки.
- `contracts/` — API-контракты. `tests/acceptance/`, `tests/e2e/` — приёмочные и E2E.
- `docs/tz.md` — ТЗ организаторов как есть. `docs/tz-analysis.md` — разбор: **сценарий демо**, требования `R*`, критерии жюри. `docs/prd.md` — что строим (задачи ссылаются на `R*`). `docs/architecture.md` — как устроено. `docs/playbooks/` — таймлайн, чек-листы и правила Issues (`issues.md`: статусы, метки, Definition of Ready).
- `events/` — правила текущего хакатона (время, состав команды).
