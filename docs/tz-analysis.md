## 1. Сценарий демо (1 минута)

Что жюри увидит, чтобы мы победили. Скоуп выводится отсюда.

| Шаг | Что делает пользователь | Что видит жюри | Требования |
|---|---|---|---|
| 1 | Добавляет «Молоко» и «Хлеб» | Товары появляются в списке, счётчик «осталось 2» | R1, R6 |
| 2 | Жмёт «Добавить» с пустым полем | Под полем «Введите название», товар не добавлен | R2 |
| 3 | Кликает по «Молоко» | Зачёркнуто, счётчик «осталось 1» | R3, R5 |
| 4 | Перезагружает страницу | Всё на месте, отметка сохранилась | R6 |
| 5 | Удаляет «Хлеб» | Товар исчез, счётчик обновился | R4, R5 |

**Вау-момент:** список живёт на сервере — перезагрузка страницы не стирает данные, счётчик сразу пересчитывается.
**Запасной план, если что-то не работает на сцене:** заранее заполненный сервер (сид-данные по запросу) и записанное видео демо.

## 2. Требования

ID стабильные: на них ссылаются задачи в PRD (`req: [R1]`).

| ID | Требование (из ТЗ, своими словами) | Приоритет | В демо? | Источник в ТЗ |
|---|---|---|---|---|
| R1 | Поле ввода и кнопка «Добавить» добавляют товар | must | да | «Поле ввода и кнопка «Добавить» добавляют товар в список» |
| R2 | Пустой товар не добавляется, появляется «Введите название» | must | да | «появляется надпись «Введите название»» |
| R3 | Клик отмечает товар купленным (зачёркнут), повторный клик снимает отметку | must | да | «Клик по товару отмечает его купленным» |
| R4 | У каждого товара есть кнопка «Удалить» | must | да | «У каждого товара есть кнопка «Удалить»» |
| R5 | Сверху видно, сколько товаров осталось купить | must | да | «Сверху видно, сколько товаров осталось купить» |
| R6 | Список хранится на сервере в памяти; эндпоинты GET/POST/PATCH/DELETE `/api/items`; список на месте после перезагрузки страницы | must | да | «Список хранится на сервере» |
| R7 | Тесты на каждый эндпоинт API | must | нет (оценка жюри) | «Есть тесты на каждый эндпоинт API» |

Правило приоритетов:
- **в демо-пути** → `must`, задачи по нему — `risk:high`, делаются первыми;
- **must по ТЗ, но не в демо** → делаем упрощённо (минимально рабочая версия);
- **остальное** → `should`/`could`, по остаточному принципу; в питче — «в планах».

## 3. Ограничения

- Стек / обязательные технологии: React (web), Node.js (api).
- API спонсоров: нет.
- Деплой и формат сдачи: деплоя нет (вне скоупа); сдача — репо.
- Правила (ИИ, готовый код, раскрытие): в ТЗ не указаны. Допущение: обычные правила репетиции.
- Время: 1 час на всё.

## 6. Риски

| Риск | Вероятность | Что делаем, если случится |
|---|---|---|
| Не успеть за 1 час (React + Node + тесты) | высокая | минимальный каркас, порядок по демо, короткие тесты по каждому эндпоинту |
| Расхождение фронта и бэка по контракту | средняя | контракт `contracts/api.yaml` первым после каркаса |
| Перезапуск сервера на сцене стирает данные | низкая | на демо перезагружаем только страницу, не сервер |

## 7. Что сознательно НЕ делаем

- Вход и регистрация.
- Несколько списков.
- База данных (только память сервера).
- Деплой.
- Красивый дизайн (только аккуратный).
- Редактирование названия товара (в ТЗ не требуется).
