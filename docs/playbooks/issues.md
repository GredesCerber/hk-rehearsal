# Правила GitHub Issues

Issues — единственная очередь задач команды. Здесь всё, что нужно знать людям и агентам.

## 1. Жизненный цикл задачи

```
needs-spec ──► ready ──► claimed ──► review ──► done
    ▲            ▲          │  │
    │            └──────────┘  └──► blocked ──► (человек разобрался) ──► ready
    └── агент: «критерии непроверяемы»
```

| Статус | Что значит | Кто ставит |
|---|---|---|
| `status:needs-spec` | задача есть, но взять нельзя: нет проверяемых критериев или ждёт другую задачу | шаблон по умолчанию; planner; агент через `hk task status <id> needs-spec` |
| `status:ready` | можно брать | **только product lead или planner**, после проверки по DoR (раздел 3) |
| `status:claimed` | агент работает, идёт аренда | только `hk task claim` |
| `status:review` | PR открыт | только `hk pr open` |
| `status:blocked` | нужен человек | агент через `hk task status <id> blocked --note` |
| `status:done` / закрыт | PR смёржен | GitHub сам закрывает issue по `Closes #N` |

Статусы `claimed` и `review` руками не ставятся — только через `hk`. Если что-то сломалось — `hk task release <id>`.

## 2. Как писать задачу

**Заголовок** — глагол + результат, видимый пользователю или системе:
- ✅ «Форма входа: email + пароль, ошибка при неверном пароле»
- ✅ «API: POST /auth/login по контракту»
- ❌ «Авторизация», «Сделать бэк», «Фикс»

**Тело** — по шаблону «Задача» (`.github/ISSUE_TEMPLATE/task.yml`):
- **Цель** — одно предложение, зачем.
- **Критерии приёмки** — Given / When / Then, каждый проверяется тестом:
  ```
  - [ ] Given пользователь на /login, When вводит верные данные и жмёт «Войти», Then попадает на /dashboard
  - [ ] Given неверный пароль, When жмёт «Войти», Then видит «Неверный email или пароль», остаётся на /login
  ```
- **Контракт** — ссылка на часть `contracts/api.yaml`, если задача касается API.
- **Разрешённые пути** — какие файлы можно трогать.
- **Вне скоупа** — что точно не делаем (агенты любят делать лишнее).

**Метки** (обязательны все три вида):
- `area:<зона>` — ровно одна. Задача на две зоны → разрезать на две.
- `tier:low|mid|high` — насколько сильная модель нужна (low: тексты, мелкие правки, тесты; mid: обычная фича; high: архитектура, сквозной каркас, сложные баги).
- `risk:high` — только если ошибка дорогая (auth, данные, платежи, демо-путь). Такие PR обязательно смотрит человек.

## 3. Definition of Ready — перед тем как поставить `ready`

- [ ] Заголовок по правилам раздела 2
- [ ] Критерии приёмки проверяемы тестом, без «красиво», «удобно», «быстро»
- [ ] Одна зона (`area:*`), указан `tier:*`
- [ ] Задача на 1–3 часа работы агента; больше — разрезать
- [ ] Зависимости уже `done` (или явно написано, против каких моков работаем)
- [ ] Это **вертикальный срез**: результат можно показать или проверить, а не «слой ради слоя»

## 4. Зависимости и эпики

- Задача ждёт другую → `status:needs-spec` и строка в теле: `После #12`. Когда #12 закрыта, product lead переводит в `ready`.
- Эпик (шаблон «Эпик», метка `epic`) — пользовательский сценарий со списком задач `- [ ] #N`. Эпики агенты не берут.
- Задача #1 на любом хакатоне — **сквозной каркас** (web → api → БД, деплой, E2E hello-world). Пока она не `done`, параллельных задач в `ready` нет.

## 5. Комментарии

- Комментарии вида `<!-- hk:claim ... -->`, `<!-- hk:heartbeat ... -->` — служебные: по ним считается аренда. **Не редактировать и не удалять.**
- При `blocked` / `needs-spec` / `release` агент обязан оставить хендофф: что сделано, что мешает, где артефакты. Человек отвечает в том же issue.
- Обсуждение по задаче — в её issue, не в чате: следующий агент восстановит контекст только отсюда.

## 6. Служебные issues

| Issue | Зачем |
|---|---|
| `#ops-log` (закреплённый) | отчёты integrator'а после окон интеграции, сводки по очереди |
| issue с меткой `hk:pause` | **аварийная остановка**: пока он открыт, агенты не берут задачи. Закрыть — работа продолжится |

## 7. Кто за что отвечает

| Роль | Делает |
|---|---|
| Product lead | переводит в `ready` по DoR, держит скоуп, режет лишнее, разбирает `needs-spec` |
| Fleet operator | раз в 30–60 мин смотрит `hk status`, разбирает `blocked`, ставит/снимает `hk:pause` |
| Planner (агент) | создаёт задачи и эпики на kickoff и при перенарезке |
| Builder (агент) | берёт `ready`, сдаёт PR, честно ставит `blocked`/`needs-spec` |
| Integrator (агент/человек) | мержит, пишет в `#ops-log` |

## 8. Чего не делать

- Не назначать задачи агентам руками (assignee ставит `hk task claim`).
- Не держать в `ready` задачи без критериев «чтобы было что брать» — агент сделает не то.
- Не создавать задачи «исправить всё» и «доделать фронт» — режьте.
- Не переоткрывать закрытую задачу под новый смысл — заведите новую со ссылкой.
