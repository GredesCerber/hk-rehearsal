# Разбор ТЗ

Вход: `docs/tz.md`. Выход: `docs/tz-analysis.md` по шаблону. **Лимит 30 минут** — не уложился, фиксируй допущения и сдавай.

## Шаги
1. Прочитай `docs/tz.md` целиком, включая критерии жюри и обязательные условия.
2. **Сначала сценарий демо** (раздел 1): 3–6 шагов, которые жюри увидит за 3 минуты. Спроси себя: «что покажет, что мы решили задачу лучше других?». Один вау-момент. Запасной план на сцене.
3. **Требования** (раздел 2): каждое требование ТЗ — отдельная строка с ID `R1, R2…`, своими словами, с короткой цитатой-источником. ID не переиспользуй и не перенумеровывай — на них ссылаются задачи.
4. **Приоритеты от демо:** требование в демо-пути → `must`; must по ТЗ вне демо → `must`, но «упрощённо»; остальное `should`/`could`.
5. **Критерии жюри** (раздел 4): каждый критерий → чем закрываем и на каком шаге демо это видно. Критерий без ответа — сигнал поменять демо.
6. **Неясности** (раздел 5): вопрос + кому задать + допущение. Не жди ответа — работай по допущению.
7. **Риски** (раздел 6): особенно внешние API, данные, деплой.
8. Если доступны ECC-навыки `product-lens`, `market-research` — можно для проверки идеи, но в рамках лимита.

## Проверка перед сдачей
- [ ] Демо-сценарий есть, у каждого шага — требования R*.
- [ ] Каждое требование ТЗ имеет ID и приоритет.
- [ ] У каждого критерия жюри есть «чем закрываем».
- [ ] У каждой неясности есть допущение.
- [ ] Раздел «НЕ делаем» не пустой.

Дальше: planner пишет `docs/prd.md` и `docs/architecture.md` (навык hk-kickoff). Если ТЗ изменилось по ходу хакатона — обнови разбор, **не меняя старые ID** (новые требования — новые номера, удалённые помечай «снято»), и сообщи planner'у.
