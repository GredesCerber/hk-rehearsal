# Kickoff

Вход: `docs/tz.md` (ТЗ организаторов, критерии жюри) и `docs/tz-analysis.md` (разбор: требования `R1…Rn`, демо-сценарий).
Выход: `docs/prd.md` с блоками `hk-task` / `hk-epic`; issues создаёт **только** `hk kickoff --apply`.

**Никогда не вызывай `gh issue create` сам.** Ты пишешь PRD, код делает остальное (детерминированно и идемпотентно).
Формат блоков: `agents/skills/hk-kickoff/task-format.md` (там полный пример).

## 1. Приоритеты из демо-сценария
- Демо-сценарий из `docs/tz-analysis.md` задаёт приоритеты: требования на демо-пути — **must**, `risk: high`, идут первыми.
- Остальное — вторично; лишнее — в «НЕ делаем».
- У каждой задачи `req: [R…]` — какие требования ТЗ она закрывает.

## 2. PRD (`docs/prd.md`), не больше страницы текста + блоки
Шаблон уже лежит в `docs/prd.md`. Первая строка — шапка `<!-- hk:prd status: draft by: - at: - -->`, не трогай её до одобрения.
- Проблема и для кого (1–2 предложения).
- **Демо-путь**: 3–7 шагов, которые жюри увидит на демо, со ссылками на `R…`.
- 1–2 основных сценария. Список «НЕ делаем».
- Как закрываем каждый критерий жюри из `docs/tz.md`.
- Стек: из `hk.config.json → stack`. Генераторы каркаса: `hk.config.json → scaffold`.

Если в ECC доступны `plan-prd`, `product-lens`, `council` — используй их для черновика и проверки идеи.

## 3. Блоки задач
- **Первый блок — сквозной каркас**: `skeleton: true`, `tier: high`, `risk: high`, без `after`; генераторы из `scaffold`, web → api, деплой, E2E hello-world. Только каркасу можно `paths` вне своей зоны.
- Дальше — контракт `contracts/api.yaml` для демо-пути (`area: contracts`, `risk` не ниже `med`).
- Остальное — вертикальные срезы по 1–3 часа, **одна зона на задачу** (`paths` только внутри неё).
- Все задачи неявно ждут каркас — `after: [T1]` не пиши; `after` — только для других зависимостей.
- Критерии приёмки — `Given … When … Then …` или `Дано … Когда … Тогда …`, проверяемые тестом.
  Не можешь сформулировать — `ready: false` (станет `status:needs-spec`).
- `risk`: `low` — мелочь (не для `contracts`/`infra`), `med` — по умолчанию, `high` — демо-путь, auth, данные, платежи (+ `e2e` в `tests`).
- Эпики — блоки `hk-epic`, задачи входят в них полем `epic`.
- **У каждой `risk: high` задачи (кроме каркаса) — задача на тесты**: блок `hk-task` с `tests_for: <T>`, `area: e2e`, `tier`; `goal` и `acceptance` не нужны (берутся у основной). Основная задача сама начнёт ждать её. Другой агент пишет тесты в `tests/pending/<T>/`, исполнитель основной переносит их в `tests/acceptance/` без изменений.
- Не дроби мельче, чем «можно отдельно смержить и показать»: мелочь внутри задачи исполнитель делает сам или своими субагентами.

## 4. Цикл проверки
```
hk task lint
```
Ошибка → исправь `docs/prd.md` по `artifacts.errors` (там строка, id, правило) → снова `hk task lint`.
**Две одинаковые неудачи подряд — стоп**: покажи ошибки человеку, не крути цикл дальше.

## 5. Одобрение
1. `hk kickoff` (dry-run) — план: что создастся, статусы, порядок.
2. Покажи PRD и план человеку (product lead) и спроси «ок?».
3. Ответил «ок» → поставь шапку `<!-- hk:prd status: approved by: <его-логин> at: <ISO-время> -->`.
   **Нет ответа 20 минут** → поставь `<!-- hk:prd status: approved by: auto-timeout at: <ISO-время> -->` и напиши людям, что одобрено по таймауту.
4. `hk kickoff --apply`. Без шапки `approved` команда ответит `plan_not_approved` — не обходи это.

Ответы `--apply`: `labels_missing` → попросить человека `hk labels sync`; `kickoff_partial` → просто повторить `hk kickoff --apply` (созданные пропустятся по маркерам).

## 6. Итог
`hk status` и короткое сообщение людям: сколько задач, что в демо-пути, что вырезано.

Перенарезка скоупа: правь `docs/prd.md` и снова `hk kickoff --apply` — создадутся только новые блоки; изменённые и удалённые (`changed`/`orphan`) команда только покажет, их issues правит человек.
